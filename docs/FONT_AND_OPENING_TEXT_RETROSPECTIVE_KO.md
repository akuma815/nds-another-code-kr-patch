# 《어나더 코드: 두 개의 기억》 한글 폰트와 오프닝 글씨 작업 후기

## 먼저 바로잡을 부분: 이 프로젝트에는 실제 `korean.tbl` 파일이 없다

질문에서 말씀하신 `korean.tbl`은 보통 ROM 해킹 도구에서 사용하는 문자표를 뜻한다. 예를 들면 다음과 같은 형식이다.

```text
889E=묘
986E=지
889D=주
889C=방
```

하지만 이번 《어나더 코드》 작업에서는 이 형식의 파일을 최종 원본으로 사용하지 않았다. 같은 역할을 하되 더 많은 검증 정보를 담을 수 있도록 JSON 매핑을 사용했다.

실제 단일 기준 자료(SSOT)는 다음 파일이다.

- `workspace/config/hangul_mapping_full_candidate_20260829_v44.json`
- 최종 등록 한글: 825자
- 각 항목: 한글 문자, 게임용 2바이트 코드, 폰트 글리프 번호, 원본 글리프 상태, CP932 정의 여부, 배정 근거

```json
{
  "character": "묘",
  "code": "889E",
  "glyph_index": 1409,
  "original_glyph": "all_zero",
  "cp932_status": "undefined_in_cp932",
  "mapping_origin": "full_pool_static_selection"
}
```

따라서 아래 글에서 말하는 “문자표”는 편의상 `korean.tbl`이라고 부를 수 있지만, 정확히는 이 JSON 코드·글리프 매핑을 가리킨다.

## 1. 전체 구조부터 이해하기

한글 한 글자가 화면에 나오기까지의 흐름은 다음과 같다.

```text
번역문 속 한글
  ↓
사용 문자 825자 집계
  ↓
각 글자에 게임이 받아들이는 2바이트 코드 배정
  ↓
그 코드가 가리키는 font.bin/font_lc.bin 글리프 칸에 한글 도트 삽입
  ↓
번역문을 해당 2바이트 코드로 인코딩
  ↓
문자열을 여유 공간에 재배치하고 포인터 수정
  ↓
게임의 기존 문자 출력기가 한글 글리프를 그림
```

중요한 점은 문자표만 만들어서는 아무것도 표시되지 않는다는 것이다. 문자열 바이트와 글리프 칸이 정확히 같은 규칙으로 연결되어야 한다.

이번 작업에서 가장 많은 시간이 든 것도 예쁜 폰트를 고르는 일 자체보다 다음 네 가지를 동시에 맞추는 일이었다.

1. 게임의 코드→글리프 계산식 확인
2. 안전하게 재사용할 코드 825개 선별
3. 게임 전용 2bpp 타일 형식으로 글리프 변환
4. 길어진 번역문 재배치와 포인터 갱신

![본문 폰트와 베이크드 오프닝 그래픽의 전체 처리 흐름](assets/font_opening_retrospective/00_overview_pipeline.svg)

*그림 1. 실시간 본문은 코드·글리프 매핑을 거치지만, 이미지에 박힌 오프닝 글씨는 `data/pack` 그래픽을 별도로 해제하고 재조판한다.*

## 2. 원본 폰트 파일의 구조를 어떻게 알아냈나

NitroFS를 조사하니 본문 폰트 후보가 두 개 있었다.

- `data/font.bin`
- `data/font_lc.bin`

둘 다 정확히 280,000바이트였다. 여러 크기로 나누어 보고 실제 렌더링 결과와 비교한 끝에 다음 구조를 확정했다.

| 항목 | 값 |
|---|---:|
| 글리프 크기 | 16×16픽셀 |
| 색 깊이 | 2bpp, 픽셀값 0~3 |
| 글리프당 크기 | 64바이트 |
| 글리프 수 | 4,375개 |
| 내부 타일 | 8×8 타일 4개 |
| 타일 순서 | 좌상 → 우상 → 좌하 → 우하 |
| 바이트 안 픽셀 순서 | 상위 2비트부터 4픽셀 |

16×16×2비트는 512비트, 즉 64바이트다. 파일 크기 역시 `280000 / 64 = 4375`로 정확히 나누어진다.

글리프 하나를 패킹하는 핵심은 다음과 같다.

```python
def pack_16x16_2bpp(glyph):
    output = bytearray()
    for tile_y, tile_x in ((0, 0), (0, 8), (8, 0), (8, 8)):
        for y in range(8):
            for group in range(2):
                value = 0
                for pixel in range(4):
                    p = glyph[tile_y + y][tile_x + group * 4 + pixel]
                    value |= p << (6 - pixel * 2)
                output.append(value)
    return bytes(output)
```

흑백 이미지 파일을 그대로 붙이는 것이 아니라, 각 픽셀을 0~3 범위의 2비트 값으로 바꾸고 NDS 타일 순서로 다시 배열해야 한다.

실제 분석·변환 코드는 다음 두 파일에 남아 있다.

- `workspace/scripts/analyze_game_font.py`
- `workspace/scripts/build_font_poc.py`

## 3. 코드와 글리프 번호의 관계

이 게임의 본문은 Shift-JIS와 비슷한 2바이트 코드를 사용한다. 다만 “CP932로 디코딩되는 문자”보다 중요한 것은 게임 자체의 글리프 계산식이다.

유효한 뒷바이트는 `0x40~0xFC`이고 `0x7F`는 건너뛴다. 선행 바이트 하나마다 188개 글리프가 배정된다.

```python
TRAILS_PER_LEAD = 188

def code_to_glyph_index(code):
    lead = code >> 8
    trail = code & 0xFF

    if 0x81 <= lead <= 0x9F:
        lead_index = lead - 0x81
    elif 0xE0 <= lead <= 0xEF:
        lead_index = lead - 0xC1
    else:
        raise ValueError("지원하지 않는 선행 바이트")

    trail_index = trail - 0x40 - (1 if trail >= 0x80 else 0)
    return lead_index * 188 + trail_index
```

반대로 글리프 번호에서 코드를 만들 수도 있다.

```python
def glyph_index_to_code(index):
    lead_index, trail_index = divmod(index, 188)
    lead = 0x81 + lead_index if lead_index <= 0x1E else 0xC1 + lead_index
    trail = 0x40 + trail_index
    if trail >= 0x7F:
        trail += 1
    return (lead << 8) | trail
```

예를 들어 `묘`에 배정된 코드는 `0x889E`, 글리프 번호는 1409다. 폰트 파일에서 이 글자의 위치는 다음처럼 계산한다.

```text
폰트 파일 시작 + (1409 × 64바이트)
```

이 연결 규칙을 먼저 확정했기 때문에 문자표, 폰트 삽입, 번역문 인코딩을 모두 같은 계산식으로 검증할 수 있었다.

## 4. 한글 825자의 코드를 어떻게 배정했나

### 4.1 완성형 한글 11,172자를 전부 넣지 않은 이유

원본 폰트에는 4,375칸밖에 없다. 게다가 일본어 원문, 기호, 숫자와 제어용 문자가 이미 그 공간을 사용한다. 완성형 한글 11,172자를 전부 넣는 방식은 처음부터 불가능했다.

그래서 최종 번역 CSV를 먼저 스캔하여 실제로 필요한 한글만 수집했다. 최종 수요는 825자였다. 문자는 CSV에 처음 등장한 순서로 고정해 빌드할 때마다 같은 결과가 나오게 했다.

### 4.2 “빈 글리프면 안전하다”는 가정도 부족했다

원본 글리프가 전부 0인 칸은 좋은 후보지만, 그것만으로 825칸을 채울 수 없었다. 최종 배정은 다음과 같이 구성됐다.

- 원본 글리프가 모두 0인 칸: 630개
- 원본에 비트맵이 있던 칸: 195개
- 합계: 825개

195개의 비어 있지 않은 칸을 무작정 덮은 것은 아니다. 다음 사용처를 함께 조사해 실제 텍스트나 리소스에서 쓰이는 코드인지 걸러 냈다.

- 원본 ROM 전체의 2바이트 코드 창
- 추출한 스크립트와 포인터 카탈로그
- 최종 번역문에 남아 있는 비한글 CP932 문자
- `data/pack` 안의 해제된 리소스
- 기존 런타임 PoC에서 이미 성공한 코드

즉 `CP932에서 정의되지 않음`, `원본 글리프가 0임`, `원문 검색에서 안 나옴` 중 하나만 보고 고른 것이 아니라 여러 근거를 겹쳐서 후보 풀을 만들었다.

### 4.3 기존에 성공한 매핑은 보존했다

초기 오프닝 대사 PoC에서 실제로 표시가 확인된 한글 코드가 있었다. 전체 문자표를 다시 만들 때도 그 코드·글리프 쌍은 그대로 보존했다. 이미 런타임에서 성공한 증거를 재배정 때문에 버리지 않기 위해서다.

최종 배정 순서는 다음과 같다.

1. 최종 번역 CSV의 한글 첫 등장 순서 확정
2. 기존 런타임 성공 매핑 우선 보존
3. 나머지를 감사된 후보 코드 순서대로 배정
4. 코드 중복, 글리프 중복, 수요 누락 검사

선택된 선행 바이트는 `81, 82, 83, 84, 85, 86, 87, 88, 96, 97, 98`이었다. 각 선행 바이트의 대표 코드를 한 화면에 표시하는 PoC를 만들어 melonDS에서 확인했다.

다만 기술적으로 정확하게 말하면 825개 모든 코드 쌍을 각각 독립적으로 시험한 것은 아니다. 대표 선행 바이트 경로, 실제 오프닝 문장, 이후 전체 플레이에서 만난 화면을 단계적으로 검증했다.

### 4.4 일반 `.tbl`이 필요하면 JSON에서 파생한다

최종 기준은 JSON으로 유지하고, 도구 호환용 `.tbl`은 다음처럼 언제든 생성할 수 있다.

```python
import json
from pathlib import Path

source = Path("workspace/config/hangul_mapping_full_candidate_20260829_v44.json")
data = json.loads(source.read_text(encoding="utf-8"))

lines = [f'{row["code"]}={row["character"]}' for row in data["mappings"]]
Path("korean.tbl").write_text("\n".join(lines) + "\n", encoding="utf-8")
```

`.tbl`은 사람이 보거나 일부 편집기에 넣기 좋지만, 원본 글리프 상태와 배정 근거까지 보존하는 JSON이 실제 빌드 기준으로는 더 안전하다.

## 5. 한글 도트 폰트는 어떻게 만들었나

최종 본문 글꼴은 `Galmuri11 Condensed` 12px를 사용했다.

| 항목 | 값 |
|---|---|
| 원본 시트 | `Galmuri11-Condensed_16x16(12px).png` |
| 시트 크기 | 1024×2800 |
| 셀 크기 | 16×16 |
| 배열 | 64열 × 175행 |
| 실제 한글 셀 | 11,172개 |
| 순서 | U+AC00 `가`부터 U+D7A3 `힣`까지 |
| 뒤쪽 패딩 | 투명 셀 28개 |
| 실제 획 크기 예 | 약 7×11픽셀 |

한글 음절의 유니코드값에서 `0xAC00`을 빼면 시트의 셀 번호가 된다.

```python
cell_index = ord(character) - 0xAC00
x = (cell_index % 64) * 16
y = (cell_index // 64) * 16
```

각 셀에서 가장 많이 나타나는 색을 배경으로 보고, 불투명하면서 배경과 다른 픽셀을 글자 획으로 판단했다. 최종 2bpp 폰트에서는 배경을 0, 획을 3으로 넣었다.

```python
pixel_value = 3 if alpha and rgba != background else 0
```

이후 16×16 픽셀을 8×8 타일 네 장으로 나누고 64바이트로 패킹하여 해당 글리프 칸에 덮었다.

![완성형 한글 시트와 실제 코드·글리프 대응 예](assets/font_opening_retrospective/02_font_mapping_and_glyphs.png)

*그림 2. 빨간 선은 16×16 글리프를 구성하는 8×8 타일 네 장의 경계다. 같은 한글이라도 유니코드값을 ROM에 직접 쓰는 것이 아니라, 아래에 표시된 게임용 2바이트 코드와 글리프 번호를 사용한다.*

### 처음부터 12px 글꼴을 확정한 것은 아니다

초기에는 작은 8×8 계열 글꼴을 2배 확대한 실험도 했고, Galmuri9 10px와 Galmuri11 Condensed 12px를 실제 기기 해상도에서 비교했다. 파일 미리보기에서 선명해 보여도 게임 화면에서는 획이 너무 가늘거나 글자가 작을 수 있었다.

결국 오프닝 첫 문장 15음절을 실제 렌더러로 표시해 보고, 크기와 가독성이 좋았던 12px Condensed를 선택했다. 최종 시트는 이미 16×16 셀이므로 2배 확대하지 않고 그대로 넣었다.

## 6. 가장 작은 PoC부터 시작한 이유

처음부터 825자와 전체 대사를 넣으면 실패 원인을 찾기 어렵다. 그래서 첫 시험에서는 일본어 한 글자 `お`의 2바이트 코드만 임시 코드 `0x96B7`로 교체하고, 그 칸에 `한` 글리프 하나만 넣었다.

화면의 기대값은 다음과 같았다.

```text
한い、着いたぜ！
```

이 이상한 혼합 문장의 목적은 번역이 아니라 세 가지를 한 번에 확인하는 것이었다.

- 새 한글 글리프가 보이는가
- 바로 뒤 일본어는 깨지지 않는가
- 글자 폭과 출력 위치가 기존 렌더러에서 정상인가

수정 범위도 정확히 등록했다.

- 대사 코드 2바이트
- 폰트 글리프 64바이트
- 합계 66바이트

빌더는 이 범위 밖의 바이트가 하나라도 달라지면 실패하도록 만들었다. 이 방식 덕분에 “일단 ROM을 만들고 실행해 보자”보다 훨씬 좁은 범위에서 원인을 추적할 수 있었다.

그다음에 실제 오프닝 첫 문장, 첫 세 화면, 선행 바이트 대표 화면, 전체 번역 순으로 범위를 넓혔다.

![melonDS에서 확인한 한 글자 한글 폰트 PoC](assets/font_opening_retrospective/01_runtime_one_glyph_poc.png)

*그림 3. 첫 PoC의 실제 melonDS 화면. 문장 첫 글자만 `한`으로 바꾸고 뒤의 일본어를 그대로 남겨, 한글 가시성과 인접 일본어 보존을 동시에 확인했다.*

## 7. 왜 `font_lc.bin`만 바꾸면 안 됐나

정적 분석 결과 시작 루틴은 `font_lc.bin`을 읽지만, 본문 제어 명령 `%u`를 처리하는 코드가 상황에 따라 `font.bin`과 `font_lc.bin`을 전환했다.

- 시작 로더: ARM9 `0x02004B60`, `font_lc.bin` 로드
- `%u` 처리 경로: ARM9 `0x0202CD14~0x0202CD4C`

초기 PoC는 `font_lc.bin` 하나만 바꾸어도 보였다. 그러나 게임 전체에서는 다른 경로로 전환되는 대사가 있으므로 한쪽 폰트만 수정하면 어떤 장면에서는 한글이 나오고 다른 장면에서는 깨진다.

최종 빌드에서는 같은 825개 한글 글리프를 다음 두 파일에 모두 기록했다.

```text
data/font.bin
data/font_lc.bin
```

이것이 “처음에는 잘 나오는데 뒤로 가면 깨지는” 종류의 문제를 막은 핵심 조치 중 하나였다.

## 8. 번역문은 어떻게 한글 코드로 바꾸었나

문자열의 한글은 JSON 문자표의 2바이트 코드로 바꾸고, 그 밖의 일본어·숫자·기호는 기존 CP932 인코딩을 유지했다.

```python
def encode_literal(text, mapping):
    output = bytearray()
    for char in text:
        if char in mapping:
            output.extend(mapping[char].to_bytes(2, "big"))
        else:
            output.extend(char.encode("cp932"))
    return bytes(output)
```

게임에는 `%w`, `%r`, `%m`, `%e`, `%h`, `%u` 같은 제어 명령도 있다. 이것들을 일반 글자로 인코딩하면 대기, 줄바꿈, 화자, 폰트 전환 같은 동작이 망가진다. 따라서 번역 CSV 검사에서 원문과 번역문의 지시문이 같은지 별도로 확인했다.

최종 번역 감사 결과는 다음과 같았다.

- 전체 카탈로그: 2,789행
- 강한 스크립트 판정 번역: 2,059행
- 보조 번역: 689행
- 승인된 번역 합계: 2,748행
- 실제 사용 한글: 825자
- 지시문 불일치: 0
- 잘못된 `%` 행: 0
- 지원하지 않는 유니코드: 0

### 번역문이 길어져서 생긴 문제

일본어 원문 칸에 번역문을 그대로 덮어쓰면 긴 문장은 다음 문자열을 침범한다. 이번 작업에서는 문자열을 개별 고정 슬롯이 아니라 연결된 클러스터 단위로 다시 배치했다.

1. 같은 데이터 구역 안의 문자열과 포인터를 수집
2. 4바이트 정렬을 지키며 번역 문자열을 연속 재배치
3. 각 문자열을 가리키는 32비트 리틀엔디언 포인터 갱신
4. 영역 용량, 겹침, 종단 바이트, 원본 보호 필드 검사

36개 승인 컴포넌트가 모두 용량 검사를 통과했고, ROM이나 개별 파일의 크기를 늘리지 않았다.

## 9. “동영상 글씨”는 실제 동영상 자막이 아니었다

이 부분이 가장 오해하기 쉽다. 화면상으로는 오프닝 영상처럼 재생되지만, 이번에 손댄 일본어 문구는 MPEG 같은 동영상 프레임에 박힌 자막이 아니었다.

오프닝은 여러 장의 게임 그래픽을 순서대로 보여 주고 효과를 합성하는 구조였다. 그래서 동영상을 디코딩하고 모든 프레임에 자막을 입힌 뒤 재인코딩한 것이 아니다.

이번 오프닝에는 서로 다른 두 종류의 글씨가 있었다.

| 종류 | 예 | 처리 방법 |
|---|---|---|
| 엔진이 실시간으로 그리는 글씨 | `13살 마지막 아침…`에 해당하는 도입 대사 | 본문 문자표와 `font.bin/font_lc.bin` 사용 |
| 이미지에 이미 박힌 글씨 | `1948年`, `父さん…`, `なぜ…!?` 등 | 압축 그래픽을 풀어 한글로 다시 조판 |

폰트를 고쳤는데도 오프닝 일본어가 남았던 이유가 바로 이것이다. 이미지에 박힌 글자는 본문 폰트 파일과 아무 관계가 없다.

### 실제 교체한 오프닝 리소스 예

| 리소스 | 원문 성격 | 한글 예 |
|---|---|---|
| `v05_bg/V5_000` | 1948년·장소 카드 | `1948년 / 블러드 에드워드섬` |
| `v05_bg/V5_007` | 1994년·장소 카드 | `1994년 / 시애틀 교외` |
| `v05_bg/V5_015` | 2005년·장소 카드 | `2005년 / 블러드 에드워드섬` |
| `v05_bg/V5_023` | 짧은 대사 이미지 | `여보…` |
| `v05_bg/V5_024` | 짧은 대사 이미지 | `왜…!?` |
| `v05_bg/V5_025` | 짧은 대사 이미지 | `앗!!` |
| `v05_bg/V5_026~030` | 후속 오프닝 문구 | `애슐리, 빨리 숨어!`, `엄마…`, `완성했다…`, `드디어…`, `리처드…` |

리소스 파일명과 재생 순서는 그대로 두고 그림 내용만 교체했으므로, 기존 오프닝의 타이밍과 전환 코드는 바꾸지 않았다.

![1948년 오프닝 카드의 일본어 원본과 한글 재조판 비교](assets/font_opening_retrospective/03_opening_1948_before_after.png)

## 11. 8×8 타일이 화면에서 옆으로 말려 있던 문제

오프닝 이미지를 처음 래스터로 풀었을 때 글자가 화면 좌우로 갈라지고, 타일 경계 뒤 내용이 8픽셀 아래로 밀렸다. 처음에는 화면 한 행을 64픽셀 순환시키면 될 것으로 생각했지만 틀렸다.

원인은 저장 단위가 픽셀 행이 아니라 8×8 타일 스트림이라는 점이었다. 최종 편집 캔버스는 전체 타일 스트림을 왼쪽으로 8타일 이동한 뒤 화면 형태로 풀었다.

```text
원본 tiled8 저장 스트림
  ↓ 전체 스트림을 왼쪽 8타일 순환
256×192 편집용 화면
  ↓ 일본어 제거와 한글 조판
역변환
  ↓ 오른쪽 8타일 순환
원래 tiled8 저장 순서
```

오프닝 자산의 변환 설정에 `layout=tiled8_sequence`, `shift_x=-64`가 기록된 이유다. `-64픽셀`은 8픽셀 타일 8개의 폭이다.

`V5_025`처럼 원래부터 화면 좌표와 맞는 일부 자산은 `raster_rows`, 이동 0을 사용했다. 모든 자산에 같은 변환을 강제로 적용하면 오히려 뒤집히거나 위치가 깨진다.

## 12. 이미지 위 한글은 어떻게 조판했나

최종 베이크드 그래픽 글꼴은 사용자가 선택한 `PF스타더스트 3.0 Bold.ttf`였다. 본문용 Galmuri와 오프닝·메뉴용 글꼴은 목적이 다르므로 별도로 선택했다.

오프닝 글씨 작업 순서는 다음과 같다.

1. 일본어가 있던 영역만 `cleanup_box`로 등록
2. 그 영역을 해당 이미지의 실제 배경 팔레트 인덱스로 복원
3. TTF를 지정 크기로 렌더링
4. 임계값 128로 1비트 마스크 생성
5. 마스크를 1픽셀 팽창시켜 외곽선 생성
6. 원본 자산에 실제 존재하는 팔레트 인덱스로 외곽선과 본문을 기록
7. 글자 중심 좌표와 변경 허용 상자를 검사

최종 오프닝 설정의 대표값은 다음과 같다.

- 연도·장소 카드: 20px
- 일반 오프닝 문구: 24px
- `여보…`: 26px
- `앗!!`, `왜…!?`: 28px
- 외곽선: 1픽셀
- 본문 인덱스: 주로 255
- 배경·외곽선 인덱스: 자산마다 원본에서 실제 사용된 값

```python
font = ImageFont.truetype(font_path, size)
mask = compose_ttf_text_mask(font, text, threshold=128)
outline = dilate_binary_mask(mask, radius=1)

paste_mask(index_pixels, width, height, outline, center, outline_index)
paste_mask(index_pixels, width, height, mask, center, ink_index)
```

글자를 RGB 색으로 직접 칠하지 않고 “팔레트 번호”를 기록한 것이 핵심이다. 게임은 같은 픽셀 인덱스라도 장면별 런타임 팔레트로 다른 색을 낼 수 있기 때문이다.

### 실제로 겪은 실패

초기 빌드에서는 한글 획 일부가 검거나 회색 블록으로 바뀌었다. 원본 자산에 없던 팔레트 인덱스를 새로 사용했기 때문이다.

예를 들어 두 자산의 배경 인덱스를 잘못 추정했다.

- `opening_why`: 150으로 썼다가 원본 유효값 239로 수정
- `opening_richard`: 16으로 썼다가 원본 유효값 23으로 수정

이후 생성기는 배경, 본문, 외곽선에 선언한 모든 인덱스가 원본 자산에 실제 존재하는지 검사하도록 강화했다. 팔레트 기반 게임에서는 “화면에서 비슷한 색”보다 “원본에 존재하는 정확한 인덱스”가 더 중요했다.

최종 그래픽 조판 코드는 다음 파일에 남아 있다.

- `workspace/scripts/build_pfstardust_graphics.py`
- `workspace/config/pfstardust_graphics_v19.json`
- `workspace/config/graphics_font_sources_v19_pfstardust.json`

## 13. 수정한 PNG를 다시 게임에 넣는 과정

편집된 PNG는 그대로 ROM에 넣을 수 없다. 다음 역과정을 거쳤다.

```text
인덱스 PNG
  ↓ 편집 캔버스 변환을 역으로 적용
4bpp/8bpp 원본 타일 또는 선형 픽셀 형식
  ↓ 원래 wrapper 형식으로 압축
pack 아카이브 재구성
  ↓ 0x20 정렬과 descriptor 갱신
NitroFS 리소스 교체
  ↓
NDS ROM 생성
```

압축 자산은 새 데이터가 기존 슬롯 용량을 넘지 않는지 확인했다. 아카이브 항목은 0x20 정렬을 유지했고, 다시 ROM에서 읽어 해제했을 때 편집 PNG와 같은 픽셀 인덱스가 나오는지 검증했다.

최종 누적 그래픽 빌드에는 오프닝 외 UI와 퍼즐 화면까지 포함해 59개 리소스의 65개 편집 캔버스가 들어갔다.

## 14. 최종 검증에서 확인한 것

폰트와 그래픽은 “ROM이 만들어졌다”만으로 완료라고 볼 수 없다. 최종 파이프라인에서는 다음을 검사했다.

### 텍스트·폰트

- 번역 CSV 보호 필드와 원문 바이트 일치
- 제어 지시문 보존
- 지원하지 않는 문자 0
- 한글 825자의 코드·글리프 일대일 대응
- 두 폰트 파일의 글리프 재읽기
- 문자열 영역 용량과 겹침 검사
- 모든 등록 포인터의 목적지 재확인
- 두 번 독립 빌드한 ROM의 바이트 일치

### 그래픽

- 편집 캔버스 65/65 존재
- 원본 헤더·팔레트 보호
- 결과 픽셀 인덱스가 허용된 원본 인덱스 집합 안에 있음
- 압축 type 01 자산 65/65 재압축→재해제 일치
- 아카이브 28/28 정렬 검사
- descriptor 65/65 재읽기
- ROM에서 decoded resource 65/65 재읽기
- NDS 헤더, FAT, 파일 경계 무결성

정적 검증 뒤에도 melonDS에서 콜드 부팅하고 실제 저장 파일로 진행했다. 세이브스테이트는 이전 ROM의 RAM·VRAM 상태를 품을 수 있으므로 새 ROM 검증의 증거로 사용하지 않았다.

## 15. 작업하면서 얻은 교훈

### 1) 문자표는 출발점이지 완성품이 아니다

`889E=묘` 한 줄을 적는 것은 쉽다. 그 코드가 실제 렌더러에서 허용되는지, 어느 글리프를 가리키는지, 다른 데이터와 충돌하지 않는지까지 확인해야 비로소 사용할 수 있다.

### 2) “안 쓰는 코드”는 한 가지 검색으로 결정하면 안 된다

원문 스크립트에 없더라도 ROM의 다른 테이블이나 압축 리소스에서 쓸 수 있다. 반대로 원본 글리프가 비어 있어도 제어 경로에서 특별 취급할 수 있다. 정적 사용처 조사와 작은 런타임 PoC가 모두 필요하다.

### 3) 폰트 파일이 여러 개면 전환 코드를 찾아야 한다

한 장면에서 성공했다고 전체 게임이 성공한 것은 아니다. 이번에는 `%u`가 두 폰트를 바꾸고 있었고, 최종적으로 둘 다 같은 한글을 넣어야 했다.

### 4) 영상처럼 보인다고 영상 파일은 아니다

오프닝 글씨가 남았을 때 영상 코덱부터 찾았다면 큰 우회를 했을 것이다. 먼저 한 프레임을 멈춰 보고 글자가 배경과 함께 움직이는지, 별도 레이어인지, 반복되는 그래픽 자산인지 분류하는 것이 중요하다.

### 5) 인덱스 이미지는 색이 아니라 번호를 편집해야 한다

일반 이미지 편집기로 RGB 변환 후 저장하면 팔레트 순서가 바뀌거나 새 인덱스가 생긴다. 화면상 비슷해도 게임에서는 글자색, 버튼색, 투명도가 완전히 달라질 수 있다.

### 6) NDS 타일 순서는 화면 좌표와 다를 수 있다

좌우가 갈라지거나 8픽셀 단위로 내려가면 글자 위치보다 타일 스트림의 시작점과 순환을 먼저 의심해야 한다.

### 7) 미리보기와 실기는 별개의 관문이다

PNG가 정상이어도 런타임 팔레트, 2D/3D 합성, 뒤집기 플래그, VRAM 캐시 때문에 실제 화면은 다를 수 있다. 그래서 정적 검사와 콜드 부팅 실기 검사를 분리해서 기록했다.

## 16. 다른 NDS 게임에 적용할 때의 권장 순서

1. 원본 ROM의 해시와 게임 코드를 고정한다.
2. NitroFS에서 폰트 후보를 찾고 파일 크기·타일 구조를 분석한다.
3. 코드 한 개와 글리프 한 개만 바꾸는 PoC를 만든다.
4. 인접 일본어와 제어 문자가 정상인지 확인한다.
5. 최종 번역문에서 실제 필요한 한글만 집계한다.
6. 빈 글리프, ROM 사용 코드, 압축 리소스 사용 코드를 교차 감사한다.
7. 코드→글리프 매핑을 JSON 같은 기계 검증 가능한 형식으로 고정한다.
8. 글꼴 후보를 실제 게임 해상도에서 A/B 비교한다.
9. 폰트 전환 경로가 있는지 ARM9와 오버레이를 확인한다.
10. 문자열 길이 초과는 클러스터 재배치와 포인터 갱신으로 해결한다.
11. 남은 일본어를 본문, 베이크드 2D 그래픽, 3D 텍스처로 분류한다.
12. 그래픽은 팔레트 인덱스와 타일 순서를 보존해 다시 넣는다.
13. 빌드를 두 번 수행해 결과가 바이트 단위로 같은지 확인한다.
14. 새 ROM을 콜드 부팅하고 일반 세이브로 실제 진행한다.

## 17. 짧은 공개용 답변

> 이번 작업은 일반적인 `korean.tbl` 파일 하나를 만들어 끝낸 방식은 아니었습니다. 최종 번역에서 필요한 한글 825자를 뽑고, 게임이 쓰는 Shift-JIS형 2바이트 코드와 4,375칸짜리 16×16 2bpp 폰트의 글리프 번호를 일대일로 연결했습니다. Galmuri11 Condensed 12px 시트에서 해당 한글 셀을 가져와 NDS의 8×8 타일 네 장 형식으로 패킹했고, 게임 중 `font.bin`과 `font_lc.bin`이 전환되는 것도 확인해 두 파일 모두 수정했습니다. 긴 번역문은 기존 칸에 단순 덮어쓰기하지 않고 같은 데이터 영역 안에서 재배치한 뒤 포인터를 다시 연결했습니다.
>
> 오프닝 글씨는 진짜 동영상 프레임에 자막을 입힌 것이 아니었습니다. 화면상 영상처럼 보이지만 일본어 문구 대부분은 `data/pack` 안의 압축된 4bpp/8bpp 인덱스 그래픽에 박혀 있었습니다. ARM9의 LZSS 계열 해제 방식을 재현해 그림을 꺼내고, 8×8 타일 스트림의 어긋난 시작점을 바로잡은 편집용 PNG에서 일본어 영역을 지운 뒤 PF스타더스트 Bold로 한글을 조판했습니다. RGB 색을 쓰지 않고 원본 팔레트 인덱스만 사용했으며, 다시 타일 순서로 돌려 압축·재삽입했습니다. 반면 오프닝 도입 대사처럼 엔진이 실시간으로 그리는 글씨는 앞의 본문 폰트 방식으로 처리했습니다.
>
> 가장 큰 교훈은 “문자표”, “폰트”, “문자열”, “그림에 박힌 글자”를 서로 다른 문제로 나누어야 한다는 점이었습니다. 한 화면에서 한글 한 글자만 성공시키는 PoC부터 시작하고, 코드 충돌·두 폰트 전환·팔레트 인덱스·타일 순서를 각각 검증한 뒤 범위를 넓히는 것이 오히려 가장 빠른 길이었습니다.
